# Zone GC 설계 메모 (임시)

구현과 실행 방법은 [08-gc-implementation.md](08-gc-implementation.md)에 정리했다.

GC 구현 전에 결정한 사항을 순서대로 기록한다. 벤치마크 방식, M3 기능 테스트의 상위 성공 기준, GC 전략의 주입·선택 방식, 첫 전략의 동작과 정상 재시작 시 상태 복원 방식을 정했다. 테스트 실행 옵션과 GC 실패 후 예비 존 처리 등은 아직 결정하지 않았다.

## 벤치마크 방식 — 결정됨

벤치마크는 **서로 독립적인 두 번의 실행**으로 나눈다. 두 실행은 매번 동일한 초기 장치 상태에서 시작하며, 같은 `fio` 설정과 재현 가능한 쓰기 패턴을 사용한다. 실행 중 조회 작업이 성능 수치에 섞이지 않도록 하는 것이 분리의 목적이다.

### 1. 성능 벤치마크

상위 `/dev/mapper/...` 장치에 `fio`를 실행하고 JSON 결과에서 bandwidth(MiB/s), IOPS, completion latency의 p50·p95·p99·p99.9를 수집한다. 이 실행 중에는 `blkzone report`나 주기적인 `dmsetup status` 조회를 하지 않는다. GC 때문에 사용자 I/O가 기다리는 시간은 측정값에 포함한다.

### 2. 공간 효율 벤치마크

1번과 동일한 초기 상태 및 `fio` workload로 **별도 실행**한다. `fio`가 동작하는 동안 외부 샘플러가 짧은 간격으로 하위 장치의 `blkzone report`와 엔진의 `dmsetup status`를 함께 조회한다. 사용자 I/O나 `fio` 프로세스를 일시정지하지 않는다. 각 샘플에는 시각과 누적 사용자 쓰기량을 연결하여 유효 데이터 비율의 변화를 본다.

실행 중 두 조회는 원자적이지 않으므로 중간 샘플의 비율은 추세를 보는 근사치다. 시작 전과 `fio` 종료 후에는 I/O가 없는 상태에서 스냅샷을 남긴다. 이 실행에서 얻은 `fio` 처리량·지연 시간은 샘플러의 영향을 받을 수 있으므로 **1번의 성능 결과로 사용하거나 직접 비교하지 않는다**. 구체적인 샘플 간격과 workload는 별도로 결정한다.

### 별도 M3 기능 테스트 — 성공 기준 결정됨

[07-milestones의 M3 성공 기준](07-milestones.md#m3--gc--zone-reset-사이클)을 벤치마크와 별도인 acceptance test로 구현한다. 상위 DM 장치의 실제 사용 가능한 논리 용량을 `C`라 하고, `[0, 0.8C)`의 논리 주소 범위에 먼저 데이터를 쓴다. 이어서 **같은 주소 범위**에 총 `1.2C`만큼 random overwrite한다. `fio`에서는 두 실행 모두 `--size=<0.8C>`를 사용하고, 두 번째 실행의 총 쓰기량은 `--io_size=<1.2C>`로 지정한다.

GC 적용판은 `ENOSPC` 없이 완료하고 최신 데이터 readback이 일치해야 하며, 유효 블록 이동과 data zone reset이 실제로 발생해야 한다. 같은 엔진의 GC 비활성화 대조군은 공간 부족으로 완료하지 못해야 한다. 이 acceptance test는 기본 32-zone 장치에서도 실행할 수 있다. 별도의 소형 장치에서 빠르게 돌리는 테스트는 선택적인 개발용 통합 테스트이며 M3 성공 기준을 대체하지 않는다.

`C`를 정확히 정의하려면 현재 underlying 전체 크기를 그대로 노출하는 DM target을 메타데이터 존과 GC용 예비 공간을 제외한 용량으로 조정해야 한다. 구체적인 `fio` 옵션, 데이터 검증 방법과 작은 테스트 장치의 크기는 구현 단계에서 확정한다.

### 측정 지표

1. **유효 데이터 비율**: `현재 최신 매핑이 가리키는 데이터 블록 수 / 데이터 존에 기록된 블록 수`. 덮어쓰기로 무효화된 옛 블록은 분모에만 포함한다. 기록된 블록이 없을 때 비율은 `N/A`로 표시한다. Metadata zone은 양쪽에서 제외하고, 그 사용량은 별도 지표로 다룬다.
2. **I/O 처리량·지연 시간**: 1번 성능 벤치마크의 `fio` 결과.
3. **지속 가능성**: `ENOSPC` 전까지 성공한 누적 사용자 쓰기량. GC가 없는 대조군이 먼저 멈출 수 있으므로 처리량·지연 시간과 별도로 기록한다.

최종값 하나만 비교하지 않고, 동일한 workload의 누적 쓰기량에 따라 유효 데이터 비율이 어떻게 변하는지도 기록한다. 성능 수치는 같은 구간의 데이터끼리 비교한다.

### 수집 위치

| 값 | 수집 방법 |
|---|---|
| 처리량·지연 시간·성공한 사용자 쓰기량 | 상위 `/dev/mapper/...`에 직접 I/O를 보내는 `fio`의 결과 |
| 데이터 존에 기록된 블록 수 | 2번 실행에서 하위 장치의 `blkzone report`로 zone별 write pointer와 start/capacity를 읽어 합산. Full zone의 write pointer가 capacity 밖의 zone 끝을 가리킬 수 있으므로 capacity에서 상한 처리 |
| 최신 데이터 블록 수 | 2번 실행에서 GC가 정확성을 위해 유지해야 하는 reverse map/validity 상태를 엔진의 `dmsetup status`로 조회 |
| GC 횟수·이동 블록 수·zone reset 횟수 | 2번 실행에서 엔진 상태를 `dmsetup status`로 조회하여 결과 해석에 활용 |

### 계측 원칙과 대조군

- 측정만을 위한 per-write 콜백이나 추가 프록시 DM은 넣지 않는다. 프록시 DM은 최신 논리→물리 매핑을 알 수 없고, 추가 계층 자체가 I/O 경로에 영향을 준다.
- 최신 데이터 판별에 필요한 상태 갱신은 GC 알고리즘의 일부이다. `dmsetup status`는 그 상태를 읽을 때 집계·출력한다.
- GC 없는 대조군은 **동일한 엔진에서 GC 정책만 `none`으로 빌드**하여 두 벤치마크를 각각 실행한다. 매핑·계측 비용을 GC 적용판과 동일하게 하기 위함이다.
- GC 자체의 시작·종료 시각 등 상세 분석이 필요해지면 선택적으로 커널 tracepoint/eBPF를 사용할 수 있다. 기본 공간·I/O 지표 수집을 여기에 의존하지 않는다.
- `null_blk`는 기능 및 회귀 검증에 사용한다. 실제 처리량·지연 시간에 관한 결론은 FEMU 또는 실제 ZNS 장치에서 검증한다.

## GC 전략 주입 구조 — 결정됨

커널 C의 함수 포인터 테이블로 다음 두 함수를 주입한다.

- `should_gc(state)`: 현재 공간 상태 등을 보고 지금 GC를 수행할지 판단한다. 공간 부족을 판단하는 임계치도 전략에 속한다.
- `run_gc(context)`: victim 선택과 정리 방법을 결정하고 GC를 수행한다. 정책의 자유도를 victim 선택 하나로 제한하지 않는다.

첫 구현은 write 경로에서 다음 흐름으로 호출한다. 아래 코드는 역할을 설명하는 의사 코드이며, 실제 인자와 반환값·실패 처리는 구현 시 구체화한다.

```c
if (policy->should_gc(state))
    policy->run_gc(context);
```

`run_gc`는 유효 블록 확인·데이터 이동·최신 매핑 갱신·안전한 zone reset 등의 공통 기능을 재사용한다. 예비 공간을 일반 쓰기가 소모하지 못하도록 보호하는 책임은 공통 allocator에 둔다. 이 보호는 선택한 전략과 GC 활성화 여부에 관계없이 적용한다.

함수를 교체하는 것과 호출 시점을 정하는 것은 별개다. 첫 구현에서는 write 경로에서 판단하므로 idle 시간이나 주기적으로 실행되는 GC는 아직 표현하지 않는다. 그런 전략을 추가할 때는 별도 실행 경로와 필요한 동기화를 확장한다. 두 함수 구조를 모든 미래 전략을 포괄하는 최종 인터페이스로 고정하지 않는다.

### 전략 선택 방식 — 결정됨

기존 `ZNS_ENGINE` 선택 방식처럼 빌드 인자로 정책을 고른다. 아래처럼 동일한 LSM 엔진을 각각 빌드하고, 선택한 정책 구현만 교체해 링크한다. `none`은 GC 비활성화 대조군이고 `simple`은 첫 GC 정책이다.

```bash
make ZNS_ENGINE=lsm ZNS_GC_POLICY=none
make ZNS_ENGINE=lsm ZNS_GC_POLICY=simple
```

DM target 생성 인자는 기존 형식을 유지한다. 선택된 정책은 `dmsetup status`에 `gc_policy=<이름>`으로 표시하고 테스트·벤치마크 결과에도 기록한다. 정책을 바꿀 때 이전 빌드의 오브젝트가 재사용되지 않도록 빌드 절차에서 재빌드를 보장한다. 실행 중 정책 변경은 첫 구현 범위에 넣지 않는다.

## 첫 GC 전략의 시작 조건 — 결정됨

- 공통 allocator는 데이터 존 하나를 GC용 예비 공간으로 남기고 일반 사용자 쓰기에 할당하지 않는다. `none`과 `simple` 모두 같은 예비 공간과 상위 논리 용량을 사용한다.
- 첫 `simple` 정책의 `should_gc`는 다음 사용자 쓰기를 위한 일반 할당 공간이 없을 때 GC를 요청한다. 최초 구현은 ordered write 경로에서 동기적으로 판단·실행한다.
- `none` 정책의 `should_gc`는 GC를 요청하지 않는다. 일반 할당 공간이 소진되면 예비 존을 사용하지 않고 공간 부족 오류를 반환한다.
- GC를 실행해도 다음 쓰기를 위한 공간을 마련할 수 없다면 쓰기는 공간 부족 오류로 끝난다.

## 첫 GC 전략의 victim 선정과 이동 — 결정됨

`simple`의 `run_gc`는 존 번호가 낮은 곳부터 검사해, **가득 찼고 무효 블록이 하나 이상 있는 첫 데이터 존**을 victim으로 선택한다. Metadata zone, 현재 예비 존과 쓰기 불가능한 존은 제외한다. 이동할 유효 블록이 예비 존의 남은 용량에 들어가야 한다. 점수 계산이나 다른 존과의 유효 비율 비교는 하지 않는다. 적합한 victim이 없으면 `ENOSPC`를 반환한다. 거의 가득 찬 유효 데이터를 옮겨 극히 적은 공간만 회수할 수도 있으므로 매우 비효율적이다. 구현이 가장 단순한 기준선을 마련하고 이후 전략의 개선 효과를 비교하기 위해 의도적으로 선택한다.

GC는 ordered I/O 경로에서 사용자 I/O와 직렬로 실행하며 한 번에 victim 한 존만 정리한다.

1. Victim의 4 KiB 블록 중 현재 최신 매핑이 가리키는 유효 블록만 찾는다.
2. 유효 블록을 예비 존에 순차로 기록한다. 각 하위 쓰기가 성공한 뒤 해당 논리 블록의 매핑을 새 물리 위치로 바꾸고 이전 위치를 무효화한다.
3. Victim의 모든 유효 블록을 옮긴 뒤 해당 존을 reset한다.
4. 이동에 사용한 예비 존을 일반 쓰기 존으로 전환하고, reset된 victim을 다음 예비 존으로 지정한다. 다음 사용자 쓰기는 새 일반 쓰기 존의 남은 공간을 사용한다.

복사·매핑 갱신·reset 중 실패하면 victim을 reset하지 않고 오류를 반환한다. 이전에 성공한 블록 이동과 새 매핑은 유지하며, 실패한 블록의 기존 매핑은 보존한다. 실패로 예비 존 일부가 소비되었을 때 이후 할당·재시도 정책은 구현 단계에서 구체화한다.

현재 데이터 블록에는 논리 주소가 저장되지 않으므로, 유효 블록 탐색에는 물리 위치에서 논리 블록을 찾는 정보가 필요하다. 이 정보와 유효/무효 상태는 공통 계층이 관리하고 `none` 빌드에도 동일하게 유지한다.

## 정상 재시작 시 GC 상태 복원 — 결정됨

기존의 정상 target 제거 과정에서 남은 MemTable 매핑이 SSTable로 저장된다는 전제 아래, target을 다시 만들 때 SSTable의 매핑 내용을 최신 테이블부터 읽는다. 각 논리 블록에서 처음 발견한 매핑만 최신으로 채택하고 오래된 중복 항목은 무시한다. 채택한 매핑으로 물리 위치→논리 블록 정보와 존별 유효 블록 수를 다시 만든다. 이를 위해 별도의 역방향 메타데이터 형식을 디스크에 추가하지 않는다.

복원이 끝나면 write pointer가 시작 위치에 있는 빈 데이터 존 하나를 GC 예비 존으로 선택한다. 나머지 빈 존은 일반 쓰기에 사용할 수 있다. 빈 예비 존을 찾지 못한 경우의 처리와 GC 실패로 일부만 사용된 예비 존의 재시도 방식은 다음에 결정한다. 복원되지 않은 매핑을 추측해 zone reset을 진행하지 않는다.

이 방식은 시작 시 SSTable payload 전체를 읽는 비용이 든다. 정상 종료·재시작을 대상으로 하며, 갑작스러운 전원 차단이나 `fsync` 이후의 crash 복구 보장은 추가하지 않는다. `none` 빌드에서도 같은 정보를 복원해 공간 효율 측정 조건을 맞춘다.

## 후속 과제

- 대규모 장치의 메타데이터 존 재사용과 SSTable compaction
- 빈 예비 존이 없는 재시작과 GC 실패로 예비 존을 일부 사용한 경우의 재시도 정책. 첫 구현은 target 생성 또는 쓰기를 안전하게 거부한다.
