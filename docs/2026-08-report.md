# 졸업프로젝트 월간 보고서 (8월)

> *이동혁(2021086917)*

> *최현준(2021037401)*

## 요약

7월에는 상위 장치의 임의 위치 쓰기를 ZNS 장치의 순차 쓰기로 변환하는 LSM 엔진을 구현하였다. 이때 논리 주소와 실제 저장 위치의 관계는 메모리의 MemTable에서 관리하였다.

8월에는 MemTable의 매핑을 SSTable로 변환하여 ZNS 장치에 영속화하고, 정상 종료 후 다시 시작할 때 이를 복구하는 기능을 구현하였다. 또한 영속화가 끝난 MemTable을 해제하고, 읽기 경로가 메모리와 디스크의 매핑을 함께 조회하도록 확장하였다.

그 결과 Device Mapper target을 정상적으로 제거한 뒤 다시 생성하거나, 제거 후 커널 모듈까지 재적재해도 기존 데이터를 읽을 수 있게 되었다.

## 1. 개발 목표

ZNS zone에서는 다음 쓰기 위치인 write pointer부터 순서대로 기록해야 한다. 따라서 같은 logical block을 덮어쓸 때도 기존 physical sector를 수정하지 않고, 새로운 위치에 데이터를 쓴 뒤 다음 매핑을 갱신한다.

```text
logical block → physical sector
```

기존 엔진은 이 매핑을 MemTable에만 보관하였다. Target을 제거하면 실제 데이터는 장치에 남아 있어도 그 위치를 찾을 매핑이 사라졌고, 모든 매핑을 계속 메모리에 유지해야 했다.

이번 달의 목표는 다음과 같다.

- MemTable의 매핑을 ZNS 장치에 저장
- 저장이 끝난 MemTable의 메모리 회수
- 메모리와 디스크 중 항상 최신 매핑 조회
- 정상 종료 시 남은 매핑 저장
- 재시작 시 기존 매핑 복구

## 2. 매핑 영속화 설계

### 2.1 Metadata zone과 SSTable

매핑도 ZNS의 순차 쓰기 규칙에 맞춰 저장해야 한다. 이를 위해 하위 장치의 마지막 zone 하나를 metadata 전용으로 예약하였다.

```text
ZNS device
├── data zones: 실제 데이터
└── metadata zone
    ├── superblock
    ├── SSTable 0
    ├── SSTable 1
    └── ...
```

MemTable의 매핑은 logical block 순서로 정렬된 SSTable로 변환된다. 새 SSTable은 metadata zone의 write pointer에 추가하며, 이미 기록된 SSTable은 수정하지 않는다. 같은 logical block의 매핑이 여러 SSTable에 있으면 가장 최근 SSTable의 값을 사용한다.

SSTable의 header에는 entry 수, 저장 block 수, logical block 범위와 생성 순서를 기록한다. Payload에는 `logical block → physical sector` 매핑을 저장한다. 이 정보만으로 필요한 SSTable을 좁히고 내부의 정렬된 매핑을 탐색할 수 있다.

Metadata zone을 예약해도 상위 Device Mapper 장치가 노출하는 논리 주소 범위는 바뀌지 않는다. 다만 하위 장치에서 실제 data allocation에 사용할 수 있는 공간은 zone 하나만큼 감소한다.

### 2.2 MemTable flush

매핑은 다음 과정을 거쳐 영속화된다.

```text
active MemTable
→ immutable MemTable
→ flushing MemTable
→ SSTable
```

`active`는 새로운 매핑을 받는다. 일정 수의 매핑이 쌓이면 더 이상 변경되지 않는 `immutable` 상태로 전환되고, background flush가 이를 SSTable로 기록한다.

기록 중인 MemTable은 `flushing` 상태에 둔다. Flush가 진행되는 동안에도 읽기가 해당 매핑을 찾을 수 있게 하고, 다른 작업이 이를 변경하거나 해제하지 못하게 하기 위해서이다.

Flush가 성공하면 새 SSTable을 조회 목록에 먼저 등록한 뒤 flushing MemTable을 해제한다. 따라서 매핑이 메모리와 디스크 양쪽에서 동시에 사라지는 구간이 생기지 않는다.

Flush가 실패하면 MemTable을 flushing 상태에 남겨 기존 매핑을 계속 읽을 수 있게 한다. 실패 전에 실제 기록되어 write pointer가 전진한 공간은 다시 사용하지 않는다.

## 3. 최신 매핑 조회

영속화 이후에는 매핑이 메모리와 디스크 중 어느 곳에든 존재할 수 있다. 따라서 읽기는 다음 순서로 매핑을 찾는다.

```text
active
→ immutable
→ flushing
→ SSTable 최신순
→ 미매핑이면 zero-fill
```

최근 세대부터 확인하므로 같은 logical block이 여러 위치에 존재해도 마지막 write의 physical sector를 선택한다. MemTable에서 찾지 못한 경우에만 metadata zone의 SSTable을 조회한다.

이 순서는 flush 전, flush 중, flush 후에 매핑의 저장 위치가 달라져도 동일한 logical read 결과를 제공하기 위한 것이다.

## 4. 정상 종료와 재시작 복구

### 4.1 Superblock 검증

Metadata zone의 첫 block에는 superblock을 기록한다. Superblock은 SSTable이 어떤 장치 구성을 기준으로 작성되었는지 확인하기 위한 정보이다.

주요 기록 항목은 logical device 크기, zone 크기와 개수, metadata zone 번호, logical block의 sector 수이다. Target을 다시 생성할 때 현재 장치 구성과 비교하며, 값이 다르면 기존 매핑을 잘못 해석하지 않도록 생성을 거부한다.

### 4.2 종료 시 잔여 매핑 저장

Target을 제거할 때는 아직 threshold에 도달하지 않은 active MemTable이 남아 있을 수 있다. 따라서 진행 중인 작업을 끝낸 뒤 메모리에 남은 MemTable을 다음 순서로 저장한다.

```text
flushing → immutable → active
```

오래된 세대부터 저장해야 최신 active 매핑이 metadata zone의 더 뒤에 기록된다. 재시작 후에는 뒤에 기록된 SSTable이 우선되므로 마지막 overwrite 결과가 유지된다.

### 4.3 재시작 시 SSTable 복구

Target을 다시 생성할 때는 다음 순서로 복구한다.

```text
장치의 zone 정보 조회
→ superblock 검증
→ metadata zone의 SSTable header 순차 탐색
→ 최신 SSTable 우선 조회 목록 구성
```

시작할 때는 모든 매핑을 메모리로 다시 읽지 않는다. Header에 기록된 정보로 SSTable 조회용 index만 복원하고, 실제 매핑은 이후 읽기 요청에서 필요할 때 조회한다.

Data zone도 장치가 보고한 현재 write pointer부터 할당을 재개한다. 따라서 재시작 전에 기록한 데이터를 덮지 않고 새로운 위치에 이어서 쓸 수 있다.

이 복구는 target이 정상적으로 제거되면서 남은 MemTable이 SSTable로 저장되었음을 전제로 한다.

## 5. 기능 검증

검증의 핵심은 매핑이 실제로 영속화되고 재시작 후에도 같은 데이터를 가리키는지 확인하는 것이다.

MemTable flush에 대해서는 다음 내용을 확인하였다.

- SSTable 생성과 metadata zone write pointer 증가
- 영속화된 MemTable의 메모리 회수
- SSTable에만 존재하는 매핑 조회
- Flush된 block을 다시 썼을 때 최신 값 반환
- 미기록 logical block의 zero-fill

재시작에 대해서는 다음 내용을 확인하였다.

- MemTable에 남아 있던 매핑의 정상 종료 시 저장
- Target 재생성 및 모듈 재적재 후 데이터 복구
- 재시작 전후 overwrite에서 최신 값 유지
- 재시작 후 새로 기록한 데이터의 다음 재시작 시 복구
- Superblock과 현재 장치 구성이 다를 때 target 생성 거부

이를 통해 background flush로 생성된 SSTable과 정상 종료 시 생성된 SSTable이 모두 복구 경로에서 사용됨을 확인하였다.

## 6. 결과 및 의의

이번 달 작업으로 MemTable의 매핑을 ZNS에 적합한 append-only SSTable로 저장할 수 있게 되었다. 영속화가 끝난 MemTable은 해제하고, 필요한 매핑은 디스크에서 다시 조회할 수 있다.

또한 정상 종료 시 남은 매핑을 저장하고 재시작 시 이를 복구함으로써 target 재생성과 모듈 재적재 이후에도 기존 데이터를 읽을 수 있게 되었다.

7월에 random logical write를 sequential physical write로 변환하는 데이터 경로를 구현했다면, 8월에는 그 변환 관계를 보존하는 metadata 경로를 추가하였다. 이를 통해 LSM 엔진이 정상적인 종료와 재시작 lifecycle을 지원하게 되었다.

## 7. 현재 한계와 향후 계획

현재 보장하는 범위는 정상 종료 후 재시작이다. 전원 차단이나 커널 패닉이 발생하면 아직 MemTable에만 존재하는 매핑이 유실될 수 있다. 또한 `fsync`가 하위 데이터뿐 아니라 매핑의 영속성까지 보장하도록 연결되어 있지 않다. 비정상 종료 복구를 위해서는 WAL과 명확한 metadata 기록 순서가 필요하다.

재시작 시 SSTable payload 전체 CRC, entry 수, key 순서와 범위, sequence를 검증하며, 불완전하거나 손상된 metadata가 있으면 target 생성을 fail-closed로 거부한다. 부분 SSTable write가 발생한 실행 중에는 손상 record 뒤로 metadata append를 계속하지 않는다. 다만 손상된 metadata zone을 자동 repair하거나 교체하는 기능은 아직 없다.

Data write는 하위 4 KiB write 성공 후에만 mapping을 공개한다. 실패 시 실제 zone WP가 움직이지 않았을 때 reservation을 되돌리므로 기존 mapping을 보존한다. 현재는 모든 LSM I/O가 하나의 ordered workqueue를 지나 정확성을 확보하므로, zone 사이 병렬화는 후속 성능 개선 과제다.

현재는 SSTable compaction과 zone garbage collection이 없어 오래된 매핑과 data block의 공간을 회수하지 못한다. 이후 유효 block 추적, data 이동과 zone reset을 결합하여 공간을 재사용할 수 있도록 확장할 예정이다.

LSM 엔진은 sector 정렬 partial I/O를 내부 4 KiB read-modify-write로 처리한다. 파일시스템 연동은 ext4 roundtrip과 fsync 이후 mapping durability를 분리해 추가 검증해야 한다.
